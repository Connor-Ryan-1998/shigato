# shigoto Plan 2: Billing Service, Org Settings and Property Module

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Self-managed QLD leases produce rent and bond invoices automatically. Each invoice is issued and sent through one reusable billing service. Arrears and bond status can be seen per lease.

**Architecture:** Move the issue, send, void and pay-options logic out of `internal/httpapi` into a new `internal/billing` package, so HTTP handlers and the scheduler both call it. Add an org settings API. Add `internal/property` (schema, CRUD, pure rent-period maths, rent run, bond) as the `property` module, wired through the existing `httpapi.modules` registry. An in-process daily scheduler runs the rent run and prunes sessions.

**Tech Stack:** Go 1.27 stdlib, pgx/v5, stripe-go v87, Postgres 18.6. No new dependencies.

**Spec:** `docs/design.md`. Follow-ups list: `docs/superpowers/plans/2026-11-05-01-followups.md`, section "Start of Plan 2".

## Global Constraints

Everything in Plan 1's Global Constraints still applies:
- Integer cents only.
- `org_id` on every query.
- Gap-free numbering, assigned at issue.
- Stripe is not the source of truth.
- Webhooks are idempotent.
- Exact image pins.
- No MRE code.
- Toolchain is Go, Docker and go-task.

Added for Plan 2:
- **New schema:** new migration files only (`0003_…`, `0004_…`). Never edit an applied migration.
- **QLD payment methods:** rent and bond invoices must offer at least 2 payment options, one of them fee-free. This rule is enforced in `billing.Issue`, so no caller can skip it.
- **Rent in advance:** a rent invoice covers exactly one period and is due on that period's start. Weekly and fortnightly rent is therefore never more than 2 weeks ahead, and monthly rent never more than 1 month.
- **Proration:**
  - The daily rate is weekly rent ÷ 7, fortnightly rent ÷ 14, or monthly rent × 12 ÷ 365.
  - Round each segment half away from zero.
  - A full period at one rate is charged the period amount exactly, never as a sum of days.
- **Rent increases** are stored in `lease_rent_changes` with an `effective_date`. More than one increase inside 12 months produces a warning, not a block.
- **Bond:**
  - Invoice source `bond`, GST code `N-T`.
  - Status is derived: `due`, then `held` once its invoice is paid, then `lodged` once an RTA reference is recorded. Spec ruling: deriving it avoids a stored status that can drift.
  - Warn when the bond is held but not lodged more than 10 days after payment.
- **GST code on rent and charge lines:**
  - Residential property: `INP`.
  - Non-residential property, org GST-registered: `GST`.
  - Non-residential property, org not registered: `FRE`.
- **Dates** use `Config.Location` (default `Australia/Brisbane`), and so does `PaidOn`.
- **Dependencies:** none new.

## Review Focus

1. **Monthly lease anchored on the 29th, 30th or 31st.** The period after 31 Jan ends on 28 or 29 Feb, and later periods anchor back to the 31st where the month has one, so there is no drift. Test in Task 4.
2. **Lease ends or is terminated part-way through a period.** The final period is prorated, and no period is generated after the end date. Test in Task 4.
3. **Rent run triggered twice at once** (two processes, or the scheduler plus a manual run). Expect exactly one `rent_period` and one invoice per lease and period. Test in Task 5.
4. **Existing lease entered with `paid_to_date` weeks in the past.** The catch-up generates every missed period up to the invoicing window, once only. Arrears include `opening_arrears`. Test in Tasks 4 and 5.
5. **Rent change effective mid-period.** The period is split and each part prorated at its own rate. A change dated before `paid_to_date` does not alter periods already invoiced. Test in Task 4.

**Interfaces:**
- Produces (pure, in `periods.go`; no DB, no clock):

```go
type Frequency string // "weekly" | "fortnightly" | "monthly"
type RentChange struct{ Effective time.Time; Amount core.Cents }
type Charge struct{ Description string; Amount core.Cents; Start time.Time; End *time.Time }
type LeaseTerms struct {
	Start      time.Time
	End        *time.Time // min(end_date, termination_date) after load
	Frequency  Frequency
	PaidTo     *time.Time
	Changes    []RentChange // sorted, first.Effective <= Start
	Charges    []Charge
}
type Period struct {
	Start, End time.Time // inclusive dates, UTC midnight
	Rent       core.Cents
	Charges    []ChargeLine // {Description; Amount}; each charge active on Start, prorated with the period
}
// PeriodsToInvoice returns every period whose Start is after PaidTo (or >= Start if PaidTo nil)
// and whose Start <= asOf + leadDays, stopping at End. Pure and deterministic.
func PeriodsToInvoice(t LeaseTerms, asOf time.Time, leadDays int) []Period
func DailyRate(f Frequency, amount core.Cents) (num, den int64) // exact rational: weekly a/7, fortnightly a/14, monthly a*12/365
```

- Period boundaries:
  - Weekly and fortnightly periods step +7 or +14 days from `Start`.
  - Monthly period *n* starts on `Start`'s day of month in month *n*, clamped to that month's last day, and ends the day before the next start.
  - Every step is computed from `Start`, never from the previous step, so there is no drift.
- Amounts:
  - Use the rate effective on the period start.
  - If a change takes effect inside the period, split the period at the change date and prorate each segment as days × daily rate, rounding each segment.
  - A truncated final period, cut short by `End`, is prorated over its days.
  - A full period at one rate is charged the exact period amount.
- CRUD routes, all under `/api/v1/orgs/{org}`:
  - `POST/GET /properties` and `GET /properties/{id}`.
  - `POST /leases` takes `{property_id, tenants:[{contact_id, primary}], start_date, end_date?, frequency, rent_amount, paid_to_date?, opening_arrears?, bond_amount?}`. It creates the lease, its tenants and the initial rent change in one transaction, and needs exactly one primary tenant. Every tenant must be a `tenant`-kind contact in the org.
  - `GET /leases/{id}` and `GET /leases?property_id=`.
  - `POST /leases/{id}/rent-changes` takes `{effective_date, amount}`. The response includes `warnings:["more than one rent increase within 12 months"]` when that applies.
  - `POST /leases/{id}/charges`.
  - `POST /leases/{id}/terminate` takes `{termination_date}`.

### Task 7: In-process scheduler

**Interfaces:**
- Produces:
  - `func Run(ctx context.Context, s Jobs, every time.Duration, now func() time.Time)` runs `s.Tick` once at start and then on every tick until `ctx` is done.
  - `type Jobs struct{ Pool *pgxpool.Pool; Billing *billing.Service; Location *time.Location; PropertyEnabled bool }`.
  - `func (j Jobs) Tick(ctx context.Context, now time.Time) error`:
    - Runs `property.RunRent(asOf = now in Location)` for each org, when `PropertyEnabled`.
    - Calls `auth.PruneSessions(ctx, pool, now)`, which deletes rows where `expires_at < now`.
    - Errors for one org are logged and the remaining orgs still run.
  - `every` is 1 hour in production. Because `RunRent` is idempotent, an hourly tick is cheap and catches up after downtime.
  - A Postgres advisory lock `pg_try_advisory_lock(7414)` per tick means only one instance does the work. Release the lock at the end of the tick.
